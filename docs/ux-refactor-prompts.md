## 사용법
1. 코딩 세션에서 목표 저장소를 열고 **설계서 원문과 이 파일을 함께 첨부**한다. 원문의 링크만 읽지 못하면 파일을 제공한다.
2. 한 번에 맡기려면 아래 **P00 통합 실행** 블록만 보낸다. 실행 에이전트가 이 파일을 읽어 P01~P05를 순서대로 수행한다.
3. 나눠서 맡기려면 **P00 공통 약속을 적용한 뒤** P01부터 하나씩 붙여 넣는다. 새 세션에는 두 문서와 마지막 단계 보고서를 함께 제공하고 ‘재개 프롬프트’를 사용한다. **이미 통과한 단계는 기존 증거를 확인하고 중복 구현하지 않는다.**
4. 실패한 검사를 피하려고 건너뛰지 않는다. 자동으로 복구할 수 있는 문제는 먼저 수정하되, 실제 사람·기기 데이터가 없으면 그 확인은 미실시로 남긴다.

## P00 | 통합 실행·공통 약속
~~~text
너는 잇단음표 식빵 공방의 모바일 UX를 개선하는 구현자다. 함께 첨부된 ‘UX 리팩토링 설계서 v1.0’과 ‘UX 바이브코딩 프롬프트북 v1.0’을 먼저 읽어라. 문서가 지금 저장소와 어긋나면 문서 설명을 기계적으로 덮어쓰지 말고, 실제 코드와 기준 커밋의 차이를 기록하고 승인된 설계 의도를 보존한다.

목표: 새 사용자가 정규 진도 밖 도마에서 한 박짜리 빵을 두 번 눌러 같은 세 조각을 만든 뒤, 2등분과 3등분이 같은 한 박에서 끝나는 것을 비교한다. 실수를 되돌릴 수 있고, 음소거로도 진행한다. 기존 사람은 원래 주문으로 복귀한다.

P01(UX0) → P02(UX1) → P03(UX2) → P04(UX3) → P05(UX4) 순으로 한 단계씩 작업한다. 단계별 통과 기준을 스스로 확인해 일상적인 구현 선택은 묻지 말고 진행하되, 회귀나 파일 충돌을 무시하지 마라. 되돌릴 수 있는 범위에서 고쳐 재검사하고, 사용자 변경 덮어쓰기나 설계 변경 없이는 해결할 수 없으면 해당 단계에서 멈춘다.

보호: 정규 43개 주문, 4개 발견 장면, 분수·잇단음표 계산, 정답표, 점수·해금과 저장 스키마 v1, 납품 즉시 저장을 그대로 유지한다. 가짜 주문 ID를 추가하지 않는다. 계산 엔진이나 정규 오디오 판정을 수정해 새 시험만 통과시키지 않는다. 실제 수정은 src/에서 하고 루트 index.html은 tools/build.mjs로 생성한다. 불필요한 패키지·분석 SDK나 외부 자원은 추가하지 않는다. 저장 데이터 초기화, 원격 쓰기, main 반영, 푸시, Vercel 배포, 실제 사용자 모집은 이 실행에 포함하지 않는다.

단계 끝마다 공통 보고서 양식으로 실제 근거를 남겨라. PASS(통과), FAIL(실패), NOT_RUN(미실행), BLOCKED(환경/결정이 필요해 진행 불가)를 구별한다. 자동 테스트로 실제 청음·실제 사람 관찰을 대신했다고 쓰지 않는다. 지금 사용자가 한 단계만 지정했다면 그 단계까지만 수행한다.
~~~

## P01 | UX0, 기준판 확보
~~~text
P00 공통 약속을 적용하고 UX0만 진행하라. 이번 단계에서는 기능 소스를 수정하지 않는다.

1. 저장소 원격 주소, 현재 브랜치, HEAD, 작업 트리 상태를 읽고 기록한다. 기준 커밋은 21eb3148d45df48a7fbca0637715830fd44c424e다. HEAD가 다르면 기준과 파일 차이를 읽되 사용자의 로컬 변경을 reset, stash, checkout으로 덮거나 옮기지 않는다. 기존 수정과 새 범위가 겹치면 안전한 격리 방법이 있는지 확인한다.
2. README.md, docs/constitution.md, docs/slice-gate-report.md, docs/device-check.md와 tools/build.mjs, tools/check.mjs, tools/progress.mjs를 읽어 필요한 런타임과 실제 실행법을 확인한다. HTML 빌드가 사용자 변경을 덮을 수 있으면 격리된 빌드 사본을 사용한다. 브라우저 의존성 부족 시 원인을 기록하고 임의 패키지로 바꾸지 않는다.
3. 가능하면 node tools/build.mjs → node tools/check.mjs → node tools/progress.mjs로 현재 기준을 실행한다. 기존 문서의 51/51, 357개 레이아웃, 43개 정규 주문·발견 4개는 비교값이지 이번 실행 결과가 아니다. 실행 로그와 종료 코드, 실패가 있다면 최초 재현 단계를 저장한다.
4. 새 브라우저 프로필/테스트 컨텍스트에서 제목→영업일→소리 확인→d0-01 흐름을 측정한다. 실제 사용자 저장은 사용하지 않는다. d0-01 첫 납품 직후 새로고침 → d0-02 이어 하기까지 검증한다. 기존 6일·43건·발견 4개는 기존 진행 테스트의 증명 범위를 명시한다. 신규·중단·완료 테스트 저장 상태는 익명 fixture로 준비한다.
5. 가능한 경우 320×568·360×640 화면의 제목/첫 주문을 캡처한다. 키보드, 오디오, 실제 기기 검증 여부를 각각 구분한다.

통과: 기준 커밋과 작업 트리 보호 방식, 주문 43·발견 4, 테스트 조건과 기존 동작 증거가 적혀 있다. 현재 기준판 자체에 기능 회귀가 있거나 핵심 재개 테스트가 실행되지 않으면 원인을 조사한다. 해결 전에는 UX1을 검증 완료 상태로 밀어붙이지 않는다.
~~~

## P02 | UX1, 무음 맛보기와 저장 분기
~~~text
P00 약속을 지키고 UX0의 결과를 읽어라. UX1만 구현한다. 실제 오디오 합성은 UX2에 맡긴다.

1. src/boot.js, src/screens.js, src/state.js, src/render.js, src/bindings.js, src/storage.js, src/shell.html, tools/build.mjs의 순서를 확인한다. 기존 #test·#주문·#발견 직행을 먼저 보존하고, 기존 유효 active가 그다음 우선이다. 정규 완료·해금 이력이 있거나 맛보기를 이미 끝낸 방문자는 기존 화면을 사용한다. 완전 신규만 별도 screen:"intro"로 진입시킨다.
2. 새 src/intro.js에 순수 전이와 UI 연결을 분리한다. 최소 상태는 { stage:"cut" | "compare", cuts:0 | 1 | 2 }. CUT은 0→1→2만, 2에서 비교로 이동한다. 비교 화면에서 연타해도 추가 컷이나 정규 진입으로 이어지지 않는다. UNDO는 2→1 또는 1→0만, 0에서는 비활성이다. 버튼과 이벤트를 한 번만 바인딩하고 포인터·키보드에 중복 발화가 없게 한다.
3. 화면 문구를 넣는다. 제목 ‘같은 한 박, 다른 조각’, 지시 ‘이 빵을 똑같이 세 조각으로 나눠요’, 상태 ‘칼집 1개, 2조각’ → ‘칼집 2개, 3조각’. 빵 전체가 button이다. 내부 칼집은 1개일 때 1/2, 2개일 때 1/3·2/3 위치에 자동 배치한다. 정밀한 좌표·속도로 채점하지 않는다. 비교에서는 길이가 같은 두 줄과 ‘조각 수가 달라도 둘 다 한 박이에요’, 그다음 ‘8분음표 셋잇단음표’와 숫자 3 악보를 보여 준다. UX1 시점에는 재생 버튼이 작동한다고 가장하지 않는다.
4. 다음 주문/건너뛰기 버튼을 따로 두고 단발로 진입시킨다. introSeen은 기존 settings 읽기·기본값 병합 방식에 추가한다. 맛보기 중 active·days·점수·레시피·빵 기록은 쓰지 않는다. 정규 진입 때만 기존 소리 확인 통과 의미와 최초 코치 상태가 일치하도록 advanceTutorial(1) 경로를 연결하고, openDay("d0",{checkSound:false})로 기존 d0-01을 연다. 단계 2~4는 유지한다. 로컬 저장 실패 시 기존 메모리 동작을 보존한다.
5. 새 마크업·스타일을 빌드 구획에 등록하고, 별도 tools/intro-check.mjs에서 전이와 진입의 테스트를 늘린다. 320×568, 360×640, 800×600에서 검사한다. 핵심 버튼 목표 44×44 CSS px. 제목·빵·다음 행동이 겹치지 않게 하고, 낮은 화면이나 큰 글꼴은 세로 스크롤을 허용한다. Enter/Space, 단계 전환 시 포커스, 정적 비교 및 상태 메시지를 확인한다. 매 프레임 aria-live 변경은 금지한다.

통과: 신규 2회 탭으로 비교, 무음/되돌리기/건너뛰기 가능, 기존 진행과 해시 우선순위 유지. IN-01~IN-05 및 UI-01의 UX1 범위를 확인한다. 저장 비교는 맛보기 상태와 ‘정규 진입 직후’를 구분한다. 작은 화면 캡처와 변경 파일을 남긴다.
~~~

## P03 | UX2, 한 박 비교 오디오·시각 재생
~~~text
UX1 통과 보고서를 읽고 두 비교 버튼을 실제로 작동시켜라. 기존 정규 음원과 판정 엔진은 수정하지 말고 저수준 시계·스케줄러·취소 구조만 재사용하라.

1. src/audio.js 등의 planRun, addListen, planScene 구현을 확인한다. 이들은 준비박·반복·여러 빵을 전제로 하므로 맛보기에 통째로 부르지 않는다. 맛보기 전용 순수 재생 계획 함수를 만들어 (2등분 시작 [0,1/2], 3등분 시작 [0,1/3,2/3], 양쪽 종료 1박)을 출력한다. 60 BPM 테스트에서 전체 시각 구간은 각각 1초다. 종료선에서 조각음을 한 번 더 넣지 않는다. 음 길이·잔향과 다음 박의 경계를 혼동하지 않는다.
2. [두 조각 듣기], [세 조각 듣기]는 선택한 줄 하나만 재생한다. 같은 템포·음색·볼륨을 사용하고, 시각 재생선은 양쪽에서 동일한 폭·종료를 갖는다. 선택된 행과 현재 조각을 텍스트/형태로도 표시한다. 실제 사용자 동작에서만 오디오 컨텍스트 시작을 시도한다.
3. 오디오가 막히거나 음소거면 ‘소리 없이도 비교할 수 있어요’와 함께 시각 재생을 진행한다. 다음 주문·되돌리기·다시 누르기는 계속 동작해야 한다. 동작 줄이기에서는 움직이는 재생선 대신 조각을 단계적으로 강조하고 정적 경계를 유지한다.
4. 세션당 활성 재생 하나를 유지한다. 재재생, 다른 버튼, 되돌리기, 다음 주문, 화면 숨김/이탈 때 예약음과 시각 타이머를 모두 취소한다. 비동기 오디오 시작이 늦게 완료되어도 화면을 벗어난 재생 토큰이면 재생하지 않는다. 정규 오디오 그룹까지 취소하지 않는다.
5. 자동 검사: 공통 종료, 각 시작점, 종료선 무음, 연타 후 재생 1건, 이동/숨김 후 콜백 없이 정리, 오류 후 시각 재생, 기존 정규 오디오 테스트. 예약을 자동 확인한 결과와 직접 귀로 들은 결과를 구분한다.

통과: AU-01의 시작점·공통 종료·취소 충족, 소리 권한과 무관하게 진행 가능. 정규 준비박, 반복 횟수, tapOffset 및 리듬 채점은 바뀌지 않았다.
~~~

## P04 | UX3, 정규 첫 주문 두 곳의 문구와 교정
~~~text
UX2 통과 보고서를 읽고 정규 첫 접점만 개선하라. 이 단계의 핵심은 먼저 정답을 알려주는 것이 아니라 다음 조작을 명확히 하는 것이다.

1. d0-01, d1-01의 실제 UI를 열어 src/board.js, src/shift-paint.js, src/coach.js, src/shell.html, 기존 바인딩을 대조한다. 0단 첫 주문은 ‘이 빵 고르기’, 1단 첫 재단은 ‘두 조각으로 썰기’처럼 기존 확정 버튼을 맥락에 맞춰 바꾼다. 버튼 ID와 접근성 이벤트는 유지한다. 첫 빵 선택 전에는 확인할 수 없게 하고, 선반과 도마 중 어디에서 행동하는지 문장으로 짚어 준다.
2. 오답이면 기존 오류 상태와 조각 수를 읽어 ‘지금은 1조각이에요. 칼집을 하나 내 볼까요?’처럼 현재 상태와 다음 조작을 짝지어 도마 옆에 보여 준다. 틀렸다고 입력을 모두 지우거나 화면을 되돌리지 않는다. 기존 설계상 강제 교정·정답 공개 시점은 그대로 둔다. 다른 주문까지 공통 슬쩍 수정하지 않는다.
3. 수동/기계 썰기 및 건너뛰기는 동등한 진도 경로를 유지한다. 입력이 불가능한 준비/진행 상태를 제외하고 기존 납품·다음 동작을 막지 않는다. actions.js의 act→record→begin("listen")을 보존한다. 납품 저장은 즉시이며, 재생 중에도 기존 다음 버튼을 사용할 수 있다. 마지막은 ‘마감하기’를 유지한다.
4. 신규/재방문, 키보드/터치, 오답→동일 도마에서 재시도, 첫 납품 직후 새로고침과 d0-02 재개를 시험한다. 기존 progress 테스트에서 진입 선택자만 필요한 만큼 조정하고 43건·6일·해금·발견 4건의 검증 자체는 유지한다.

통과: 첫 두 주문에서 어떤 버튼을 눌러야 할지가 이름으로 드러난다. 오답 후 재시도 가능하며 점수, 정답표, 상태 저장, 발견 장면 수가 기준과 같다. 기존의 실제 연주 결과를 새 진급 조건으로 넣지 않았다.
~~~

## P05 | UX4, 검증과 배포 판단
~~~text
UX0~UX3 보고서를 읽고 테스트 장부를 갱신하라. 실패를 감추기 위해 테스트를 바꾸지 말고, 문제가 처음 생긴 단계의 작은 수정으로 돌아가 해결하라.

1. node tools/build.mjs, node tools/check.mjs, node tools/progress.mjs, node tools/intro-check.mjs를 저장소의 실제 실행 환경에서 구동한다. 설계서 §6의 IN-01~05, AU-01, UI-01, REG-01~03을 모두 대응시켜 통과/실패/미실행으로 표기한다. 각 명령과 종료 상태를 적는다. 새 검사 결과를 기존 51/51과 섞지 않는다.
2. 320×568 및 360×640에서 자르기/비교/정규 첫 주문 캡처를 남긴다. 큰 글꼴, 키보드, 무음, 동작 줄이기, 앱 숨김, 연타, 재개와 레거시 저장 검사를 재실행한다. 촬영 화면이 에뮬레이션이면 그렇게 명시한다.
3. 실제 iPhone Safari/Android Chrome과 초견 5명 검증 기회가 있다면 아래 표준 문구와 양식을 사용해 결과를 기입한다. 없으면 NOT_RUN으로 두고, 테스트 시나리오와 빈 기록표만 준비한다. 테스트를 했더라도 개인정보, 영상, 이름을 저장하지 않는다.
4. 최종 보고에 구현 범위, 변경 파일, 테스트 대비표, 화면·로그 위치, 사용자 기록 보호, 실제 기기/사람 검증 상태, 남은 문제를 정리한다. 자동 테스트까지 통과했어도 실제 사용성 확인이 빠졌으면 ‘구현 완료, 실제 사용성 검증 대기’로 보고한다. 기준 미달이면 첫 막힘에 대한 수정·재검증을 제안하고 배포는 보류한다. 이 지시만으로 저장소 푸시나 Vercel 배포를 하지 않는다.

통과 목표: 5명 중 4명 이상이 도움 없이 30초 이내 세 조각을 만들고, 비교 후 두 줄 모두 같은 한 박이라고 설명한다. 칼집 2개·음 시작 3회는 별도 진단한다. 통과하지 않았거나 관찰하지 않았다면 통과라고 적지 않는다.
~~~

### 실기기·초견 기록표
안내는 “화면을 보고 한번 해 보세요”만 말한다. 비교 화면 도착 뒤 “둘 중에 어느 빵이 먼저 끝나나요?”, “칼집은 몇 개고 소리는 몇 번인가요?”라고 묻는다. 답을 먼저 가르치지 않고, 도마 화면이 보인 순간부터 비교 첫 진입까지를 잰다.

| 코드 | 실제 기기·OS·브라우저·화면폭 | 소리 상태 | 비교 진입 초 | 도움 여부·막힌 지점 | 한 박 설명 | 칼집/음 시작 | 결과 |
|---|---|---|---:|---|---|---|---|
| P1~P5 | 미기입 | 미기입 | — | 미기입 | 미기입 | 미기입 | NOT_RUN |


## 재개·실패 복구용 프롬프트
~~~text
이전 세션의 단계 보고서, 설계서와 프롬프트북을 먼저 읽어라. 현재 브랜치·HEAD·diff를 확인한다. 마지막 PASS 표기와 실제 증거가 일치하는지 확인한다. 상태를 초기화하거나 사용자 변경을 지우지 않고, 증거가 없는 확인부터 반복한다. 마지막 통과 다음 단계의 첫 미완료 작업부터 재개한다.

오류 분류: ① 기준 코드부터 재현, ② 이번 변경의 회귀, ③ 브라우저·오디오 등 환경 제한, ④ 기존 저장 호환 실패. 각각 재현 입력과 결과를 기록한다. 테스트에 실패하면 기대 결과를 삭제·완화하지 말고 재현 → 원인 분리 → 최소 수정 → 해당 테스트 및 연관 회귀 재실행 순서로 복구한다. 정규 주문이 망가졌다면 맛보기 전용 연결만 분리해 원인을 좁히되, 운영본이나 다른 작업자의 변경을 건드리지 않는다. 실제 기기나 사용자만 확인할 수 있는 항목은 미실행으로 남기고 다음 검증에 필요한 구체적 조건을 보고한다.
~~~
